# 豆包单轮语音与低延迟设计

## 目标

在不改变本地唤醒词、本地命令、评分、MIDI、UI 和既有业务逻辑的前提下，将新增豆包语音助手改为单轮交互：每次说出“你好小智”后只接收一句话，本地命令继续优先；开放式问题由豆包回答一次，播放结束后自动回到等待唤醒。

## 问题与约束

- 现有 MultiNet 的 6000 ms 超时被直接当成 AI 分流条件，导致开放式问题固定等待约 6 秒。
- AI 状态只有“持续上传”和“停止”，回答结束不会自动停止，因此 WakeNet 长期处于关闭状态。
- 回答播放期间仍持续上传麦克风，既会占用 WebSocket 写锁和输入环形缓冲，也可能把扬声器声音再次送入云端。
- 扬声器实时 PCM 缓冲仅 32 KiB，日志已经出现整块 TTS 数据因空间不足被拒绝，听感会断续。

## 方案

### S3：本地优先的句末提前分流

S3 唤醒后仍逐帧调用原 MultiNet。本地命令一旦命中，立即执行原路径，丢弃 AI 候选音频并恢复 WakeNet。

同时利用现有 AFE 的 VAD 结果，仅为开放式语音记录“有效说话”和“连续静音”时长。跳过唤醒词后的短保护窗口，并等到唤醒词之后首次静音才打开查询门，避免把“你好小智”本身发给云端；在检测到足够的查询语音，并在其后出现约 800 ms 连续静音时，如果该帧 MultiNet 仍未命中，则提前发送 `V2,AI,BEGIN`。原 6000 ms MultiNet 超时继续保留为兜底，不缩短本地命令识别窗口。

若 6000 ms 内完全没有新的查询语音，则退出候选状态并恢复 WakeNet，不建立云端连接。

### 板间状态：停止输入与结束会话分开

增加 `V2,AI,INPUT_DONE` 控制帧。S3 的本地 VAD 已确认句末并发送 `AI,BEGIN` 后，P4 立即：

1. 通知 S3 停止本轮后续麦克风传输，但暂不恢复 WakeNet；
2. 继续把此前已经可靠缓存的一句话发给豆包；
3. 豆包返回“用户输入转写完成”时再次确认停止输入并清空多余上行 PCM。

S3 进入“等待 AI 回答”状态。P4 在豆包音频结束且扬声器队列真正排空后关闭会话，再发送原有 `V2,AI,STOP`。S3 此时才恢复 WakeNet。这样可避免回答期间自唤醒，同时确保下一轮必须重新说“你好小智”。

### P4：回答播放与自动退出

豆包 `response.output_audio.started` 启动原扬声器服务的 PCM 流；`delta` 只入队；`done` 请求排空。工作任务轮询扬声器状态，确认播放完成后再结束 WebSocket 会话和本轮状态。

实时 PCM 缓冲从 32 KiB 增至 128 KiB，缓解云端分块突发导致的 `ESP_ERR_TIMEOUT`。单轮输入完成后停止上行，也会减少 WebSocket 锁竞争、输入环形缓冲溢出和扬声器回声被再次识别的问题。

## 状态流

`等待唤醒 -> 本地命令/开放问题候选 -> 本地命令完成并回到等待唤醒`

或：

`等待唤醒 -> 候选 -> 句末提前进入 AI -> 云端确认输入完成 -> 等待/播放回答 -> 播放排空 -> 关闭 AI -> 恢复等待唤醒`

## 失败恢复

- WebSocket、协议或扬声器错误仍通过现有错误事件发送 `AI,STOP`，S3 恢复 WakeNet。
- `INPUT_DONE` 丢失不会破坏最终恢复：P4 已拒绝后续音频，最终 `AI,STOP` 仍会退出 S3 的任一 AI 状态。
- 本地命令路径不建立豆包会话，不改变命令 ID、页面行为或 ACK 机制。

## 验证重点

- 本地七条指令仍命中原逻辑，无云端连接。
- 开放式短句在句末静音后约 1 秒内开始连接，而非固定等待 6 秒。
- 一轮回答播放结束后日志出现会话结束和 WakeNet 恢复；不重新唤醒时继续说话不会进入 AI。
- 连续两轮均需分别说“你好小智”。
- 长回答不再持续出现 `speaker PCM queue rejected TTS`，输入环形缓冲不再在回答期间持续溢出。
