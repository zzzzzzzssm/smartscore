# 手机结束同步与乐谱起点锁定对齐设计

## 目标

修复两个相互独立但同时影响练习结果的问题：

1. 手机小程序调用 `/api/stop` 后，设备屏幕必须结束当前演奏并自动显示与手机相同的评分结果。
2. 最终评分必须从乐谱开头建立对齐，不能因为重复音型把开头演奏吸附到乐谱后面的相似段落。

本次不改变已经确定的音准、节奏、流畅度、完成度公式和麦克风可信度规则。

## 统一结束控制

### 当前问题

屏幕结束按钮调用 `screen_adapter` 内部的完整结束流程：结束屏幕会话、停止评分服务、创建结果等待任务并切换结果页。HTTP `/api/stop` 目前直接调用 `scoring_service_stop()`，绕过了屏幕会话和结果页流程，因此手机能拿到评分而屏幕仍停留在演奏页。

### 设计

`screen_adapter` 暴露一个可从 HTTP 任务调用的公共完成入口。屏幕按钮、自动结束、语音结束和 `/api/stop` 都通过该入口请求完成当前练习。

该入口使用现有会话锁原子地认领结束操作：

- 第一个调用者把会话从 `active` 改为 `completing`，停止节拍器和录制，并启动唯一的评分结果任务。
- 评分任务完成后读取评分服务保存的同一份 JSON，并切换设备屏幕结果页。
- HTTP 处理器等待同一个评分任务产生的结果，再把同一份 JSON 返回小程序。
- 后续重复结束请求如果状态已经是 `completing` 或 `ready`，不得再次调用 `scoring_service_stop()`，只等待或读取现有结果。

屏幕对象的启用、禁用和状态文字更新继续通过显示锁保护。HTTP 超时只影响本次 HTTP 响应，不取消后台评分和屏幕结果页切换。

## 乐谱起点锁定对齐

### 当前问题

当前粗对齐是全局音高序列编辑对齐。动态规划允许在第一次匹配前连续执行乐谱漏音操作；当乐谱含有重复音型时，第一段演奏可能被匹配到后面的相似段落，造成开头大量漏音、音准分异常降低，小程序折线也出现整体错位。

### 开头锚点

评分先在有限前缀中建立不可移动的开头锚点：

- 候选乐谱范围为前 3 个音，即允许开头最多漏 2 个目标音。
- 候选演奏范围为前 3 个可靠演奏音，即允许开始前出现少量误触或重弹。
- 优先选择音高完全相同且编辑代价最低的候选对。
- 如果前缀内没有完全相同的音高，使用乐谱第一音与演奏第一音建立替代音锚点，避免搜索跳到后面的重复段落。
- 锚点之前的目标音标为漏音；锚点之前的演奏音按现有规则标为重弹或多弹。

### 锚点后的对齐

粗对齐和精细对齐只处理锚点后的两个后缀，并继承锚点建立的乐谱位置：

- 路径只能向前单调移动，不能重新选择歌曲起点。
- 起奏偏移和速度只能从锚点及其之后的可靠匹配估计。
- 精细对齐继续使用时间门限、局部速度和编辑代价恢复少量错音、漏音和多弹。
- 低可信麦克风音符仍不作为锚点，也不能推动对齐位置。

结果 JSON 增加 `start_anchor_target_index`、`start_anchor_played_index`、`leading_missing_count` 和 `leading_extra_count`，用于检查折线是否从正确位置开始。小程序继续直接使用评分结果中的 `aligned_played_start`，不再自行猜测新的对齐起点。

## 错误处理

- 没有可靠演奏音时不建立锚点，沿用当前零分或麦克风不可评分规则。
- 屏幕未准备好但评分会话存在时，HTTP 仍可结束并取得结果；屏幕切页失败需记录错误，但不得重新评分。
- 评分已开始或完成时再次点击手机或屏幕结束按钮，返回已有状态，不报“没有录制可停止”。
- 评分服务真正失败时，手机和屏幕显示同一个失败状态。

## 验收

1. 手机单独点击结束：只生成一次评分，手机收到结果，屏幕自动进入结果页。
2. 屏幕单独点击结束：屏幕显示结果，随后请求 `/api/result` 得到完全相同的 JSON。
3. 手机与屏幕几乎同时结束：只调用一次停止录制，不出现 409，不产生两份结果。
4. HTTP 等待超时：后台评分继续，完成后屏幕仍显示结果，小程序可通过 `/api/result` 重取。
5. 乐谱包含两个相同乐句，只演奏第一个乐句：演奏必须对齐第一个乐句。
6. 漏掉乐谱第一音：第一音为 `missing`，演奏第一音可对齐乐谱第二音。
7. 开头先误触再正确弹第一音：误触为 `retry` 或 `extra`，正确音锚定乐谱第一音。
8. 中途错音、漏音和停顿：锚点不改变，后续保持单调对齐。
9. 小程序折线中的目标音序号和演奏点按 `ref_index` 单调增加，不出现整段跳到后一个重复乐句。
