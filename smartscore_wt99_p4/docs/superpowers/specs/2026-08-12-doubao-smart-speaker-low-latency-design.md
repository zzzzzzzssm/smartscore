# 豆包智能音箱级低延迟语音设计

## 目标

在不改变 S3 本地唤醒词、本地 MultiNet 指令、P4 评分、MIDI、UI、AI 识谱和 AI 练习建议逻辑的前提下，将新增豆包语音助手优化为单轮、低延迟、连续播放的智能音箱式体验。

正常网络条件下的目标是：用户说完开放式问题后约 1～2 秒开始播放回答；回答过程没有因客户端缓冲欠载或整块丢弃造成的断续；播放完成后自动恢复“你好小智”唤醒。网络和豆包服务端负载不在设备可控范围内，因此延迟目标必须通过日志分段测量，而不能作为绝对保证。

## 已确认的问题

新日志暴露了三个相互独立的问题：

1. P4 在 S3 确认开放式问题后才进行 TLS/WebSocket 握手，单次握手约需 3～4 秒。
2. 候选音频先在 P4 堆积，再以 20 ms JSON/Base64 小包同步补传。发送速度有时低于音频产生速度，导致 120832～256000 字节积压、输入环形缓冲溢出和十几秒补传。
3. 回答播放直接受 WebSocket 分块节奏驱动。当前扬声器在收到 `output_audio.started` 时立即启动 I2S，尚未形成抖动缓冲；输入块空间不足时整块拒绝。日志还出现了服务端 `AudioTTSIdleTimeoutError`，即服务端报告 TTS 开始后长时间没有下发任何 PCM，这不能通过单纯扩大扬声器缓冲解决。

测试日志同时显示节拍器正在输出。S3 只有单麦克风且没有 AEC 参考通道，持续外放会干扰 VAD 句末判断。因此语音采集期间必须取得临时音频焦点。

## 方案选择

采用“常驻 WebSocket + 唤醒即建 Session + 本地和云端并行候选 + 音频焦点 + 播放抖动缓冲”的效果优先方案。

不采用以下两个方案：

- 唤醒后才连接：减少空闲连接，但第一次响应仍包含 TLS 延迟。
- 说完后才连接并仅调整超时：改动较小，但无法消除握手和积压补传，达不到智能音箱体验。

该选择的明确代价是：P4 长期占用一条 TLS/WebSocket 连接及其内部内存；每次唤醒都会短暂创建云端 Session，即使命中的是本地指令，也会产生少量云端通信。

## 总体架构

### P4 WebSocket 传输层

`voice_assistant` 将“WebSocket 传输”和“豆包 Session”拆成两个生命周期：

- Wi-Fi 连接成功且 API Key 可用时建立 WebSocket；连接空闲时不创建 Session、不上传麦克风。
- Wi-Fi 断开时停止连接；恢复后在后台重连。
- 单轮回答结束只关闭 Session，保留 WebSocket 供下一次唤醒复用。
- WebSocket 连接失败不阻塞 UI、评分、MIDI、板间通信或本地语音指令。

网络状态由 P4 现有 `manage_network_services()` 以新增的非阻塞接口通知 `voice_assistant`，不改变 Wi-Fi 配网和设备 API 的原有控制流。

### 唤醒后的并行候选

P4 收到 S3 `WAKE` 后立即执行：

1. 获取语音音频焦点；
2. 创建豆包 Session；
3. 继续接收 S3 候选 PCM；
4. Session 就绪后按稳定节奏实时上传候选音频。

S3 继续逐帧运行原 MultiNet。云端结果在 S3 作出本地/开放式分流决定前处于“候选”状态，禁止触发扬声器播放或业务行为。

### 本地命令优先

如果 MultiNet 命中原本地指令：

- S3 走原命令 ID、UART 帧、P4 页面处理和 ACK 路径；
- P4 取消云端候选响应并关闭当前 Session；
- 不播放任何云端候选音频；
- 在本地命令处理回调结束后释放音频焦点；
- 不修改原命令表、指令语义或业务逻辑。

### 开放式问题提交

如果 S3 判定为开放式问题并发送 `AI,BEGIN`：

- P4 将当前 Session 标记为已提交，允许这一轮云端输出进入播放链路；
- S3 按现有单轮协议停止后续麦克风上传，等待回答结束；
- 豆包此前已实时收到问题，无需再次等待 TLS 或突发补传；
- 回答播放排空后关闭 Session，发送 `AI,STOP`，S3 恢复 WakeNet。

## 音频焦点

P4 在 `WAKE` 时读取扬声器状态并保存最小恢复信息：

- 节拍器运行时调用现有暂停接口，保存 BPM 和拍号；
- WAV 文件播放时调用现有文件暂停接口；
- 已暂停的来源不重复操作；
- 短提示音不做持久恢复；
- 豆包回答播放期间，AI PCM 流独占扬声器。

本地命令结束、候选取消或 AI 回答结束时释放焦点：

- 若原节拍器仍应运行且本地命令没有主动改变其状态，用保存的 BPM/拍号重新启动；
- 若原 WAV 文件仍处于暂停状态，调用现有切换接口继续从当前位置播放；
- 如果业务逻辑已经停止或替换了原音源，则不恢复旧音源。

音频焦点只协调新增语音助手与现有扬声器服务，不改变练习、节拍器或文件播放的业务状态来源。

## 上行音频管线

### 帧大小和节奏

P4 将 S3 PCM 合并为每包 50 ms：16 kHz、单声道、s16le，共 800 个样本、1600 字节。该大小位于官方建议的 20～50 ms 范围上限，可以显著降低每秒 JSON/Base64/WebSocket 同步发送次数。

上传器采用单独工作任务，任何 WebSocket 发送都不在 UART RX、UI、评分或 MIDI 任务中执行。实时状态每 50 ms 最多发送一包；若连接刚恢复并存在少量积压，可用有限的追赶额度，但禁止无节奏地一次突发发送大量历史音频。

### 可重放的一句话缓存

候选 PCM 使用 PSRAM 中的单轮线性缓存，分别维护：

- `capture_length`：已可靠接收的字节数；
- `send_offset`：当前 Session 已上传的位置；
- `utterance_closed`：S3 已确认句末；
- `committed`：本地分流已经选择 AI。

正常上传不会删除已发送数据，直到本轮成功结束或本地命令取消。这样在首次 TTS 无音频时可以重建一次 Session，并从缓存开头重传完整问题。缓存达到上限时记录明确错误并停止继续写入，不能静默覆盖问题开头。

### 云端判停

Session 配置增加 ASR `end_smooth_window_ms = 500`，使用官方允许的最低值。S3 的本地 VAD 仍负责本地/AI 分流；云端 VAD 负责模型开始回答的时机。S3 已缓存的句末静音仍按正常 50 ms 帧发送，帮助云端完成判停。

## 下行播放管线

### 解码和入队

WebSocket 回调只负责：组装完整 JSON、识别事件、Base64 解码 PCM、将 PCM 写入扬声器流缓冲。较大的临时解码块优先从 PSRAM 分配，避免继续挤压 TLS 所需的内部 DMA 内存。

扬声器流写接口支持分段写入和明确的接受字节数。不能再因为当前空间不足而整块丢弃；缓冲真正耗尽时记录高水位、拒绝字节数和原因。

### 预缓冲和连续 I2S

收到 `response.output_audio.started` 时只建立流状态，不立即开启功放/I2S 数据输出。满足以下任一条件后开始播放：

- 缓冲达到约 120 ms PCM，即 5760 字节；
- 已收到 `output_audio.done`，且缓冲中存在不足 120 ms 的短回答。

播放任务固定按 512 个样本读取和写入 I2S。开始播放后，128 KiB 缓冲负责吸收网络分块抖动。若发生欠载，记录次数和最低水位并进入短暂再缓冲，而不是消费不存在的数据或丢弃后续整块。

回答 `done` 后必须先排空流缓冲和 I2S DMA，再关闭 Session、释放音频焦点并恢复 WakeNet。

## TTS 无音频恢复

收到 `response.output_audio.started` 后启动首包看门狗：

- 4 秒内收到第一个非空 `delta`：取消看门狗，正常播放；
- 4 秒内没有 PCM：关闭当前 Session，保留 WebSocket，创建一个新 Session，并从单轮缓存开头按 50 ms 节奏重传一次；
- 第二次仍无 PCM、出现协议错误或 Session 被服务端关闭：结束本轮，发送 `AI,STOP`，恢复原音频焦点和 WakeNet。

自动重试最多一次，防止错误循环占用网络、内存和云端配额。重试前尚未播放任何 PCM，因此不会产生重复播报。

## 状态机

P4 传输状态：

`OFFLINE -> CONNECTING -> WARM -> RECONNECTING`

P4 单轮状态：

`IDLE -> CANDIDATE -> COMMITTED -> RESPONSE_BUFFERING -> PLAYING -> DRAINING -> IDLE`

本地命令分支：

`CANDIDATE -> CANCELED -> IDLE`

一次无音频重试分支：

`RESPONSE_BUFFERING -> RETRYING -> CANDIDATE/COMMITTED`

WebSocket 状态和单轮状态分别受锁保护；耗时的 TLS、JSON、Base64 和扬声器调用都不能在临界区中执行。

## 日志与可测量指标

每轮生成递增 ID，并记录以下单调时间戳：

- WAKE；
- WebSocket 是否已预热；
- `session.create` 发送和 `session.created`；
- 首包上行、末包上行；
- ASR started/completed；
- AI 分流提交；
- TTS started、首个 PCM delta、done；
- 播放开始、欠载、排空；
- Session 关闭、音频焦点恢复、WakeNet 恢复。

结束日志汇总：唤醒到 Session 就绪、句末到 ASR 完成、句末到 TTS 首包、预缓冲时长、总播放时长、最低/最高缓冲水位、上行积压峰值、重试次数和错误原因。

## 错误隔离

- API Key 缺失、Wi-Fi 离线或 WebSocket 失败时，本地唤醒和本地指令继续工作。
- 预热连接占用内存低于 TLS 安全阈值时，记录并退化为唤醒时连接，不允许设备崩溃。
- UART 序号、长度、CRC、ACK/NACK 机制保持不变。
- 语音助手不得直接调用或修改评分、MIDI、AI 识谱、AI 练习建议的数据路径。
- 新增任务必须使用有界队列/缓冲，不使用无限等待阻塞现有实时任务。

## 验证方案

### 本地兼容性

逐条测试原七条本地指令，确认命令 ID、页面行为和 ACK 与改动前一致；监控中可看到候选 Session 被取消，不能听到云端候选回答。

### 延迟

在稳定 Wi-Fi、无外放干扰下连续进行十轮短问题，统计句末到 TTS 首包和句末到扬声器开始时间。目标中位数为 1～2 秒，且不再包含每轮 3～4 秒 TLS 握手。

### 外放干扰

分别在节拍器和 WAV 文件播放时唤醒。确认外放立即暂停、句末可及时识别，本地命令结束或 AI 回答结束后按保存状态恢复。

### 连续播放

测试 5 秒、15 秒和 30 秒回答。监控中不得出现常态化 PCM 整块拒绝；欠载计数应为零，回答结束后缓冲和 I2S 正确排空。

### 故障恢复

模拟 Wi-Fi 断开、WebSocket 关闭、TTS 首包缺失和服务端错误。确认最多自动重试一次，最终恢复 WakeNet，UI、评分、MIDI 和本地命令始终可用。

## 不在本次范围

- 不增加第二麦克风或硬件回采通道，不实现真正的声学 AEC。
- 不替换豆包模型、业务接口、音色、引脚或 S3↔P4 物理通信方式。
- 不改变评分结果、当前曲目或 AI 练习建议的生成逻辑。
- 不实现无需唤醒词的连续多轮对话；每轮仍必须重新说“你好小智”。
