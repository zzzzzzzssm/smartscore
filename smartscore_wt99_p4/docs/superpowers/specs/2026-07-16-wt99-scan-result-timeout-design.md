# WT99 Wi-Fi 扫描结果超时修复设计

## 实机结论

P4 串口日志显示两次扫描分别返回 24 和 23 个 AP，业务层去重后均准备向小程序发送 6 个网络。板端扫描成功，问题发生在小程序接收阶段。

第一次扫描从请求到 `WIFI_EVENT_SCAN_DONE` 约 19.6 秒，第二次约 19.3 秒。当前小程序在 15 秒时将 `wifiScanRequestId` 清空；随后到达的 `wifi_network` 和 `wifi_scan_done` 因请求 ID 不匹配被全部丢弃。

原 ESP32-S3 工程使用直接 Wi-Fi 控制器，扫描通常更快；而且原小程序的提示超时不会使后续扫描通知失效。WT99 使用 ESP32-P4 + ESP-Hosted + 双频 ESP32-C5，扫描耗时不能继续套用原工程的短超时行为。

## 方案比较

1. 保留双频扫描和请求 ID，将等待窗口调整为 45 秒，并在提示超时后继续接受同一请求的迟到结果。此方案保留 2.4 GHz/5 GHz 覆盖，并避免旧请求污染新请求。
2. 强制只扫描 2.4 GHz。扫描较快，但可能看不到未开启“最大兼容性”的 iPhone 热点。
3. 移除请求 ID 校验。行为接近原小程序，但连续点击扫描时可能把上一轮结果混入新一轮。

采用方案 1。

## 修改范围

- 只修改 `miniprogram/pages/device/device.js`。
- 扫描等待窗口使用常量 `WIFI_SCAN_TIMEOUT_MS = 45000`。
- 超时只更新界面提示，不清除当前请求 ID；收到正常完成、明确失败、页面卸载或发起下一轮扫描时再清理。
- 不修改 Wi-Fi 密码处理，不修改 BLE UUID，不修改 P4/C5 固件。

## 验证

- JavaScript 语法检查通过。
- 扫描请求 ID 在提示超时后仍保留。
- `wifi_scan_done` 会清除计时器和请求 ID。
- 用户只需重新编译微信小程序，无需重新烧录 P4 或 C5。
