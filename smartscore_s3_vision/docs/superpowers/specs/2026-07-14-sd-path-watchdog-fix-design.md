# SD 存储与任务看门狗修复设计

## 背景

固件已能在 ESP32-S3 上完成编译、烧录和启动，但运行日志暴露出两个独立问题：

- FatFS 未启用长文件名，`/sdcard/smartscore` 不符合当前 8.3 文件名约束，`mkdir` 返回 `EINVAL`，照片保存被禁用。
- `app_main` 在 JPEG 解码和手势推理连续到期时没有主动让出 CPU0，导致 `IDLE0` 长时间无法运行并触发任务看门狗。

## 目标

- 在不启用 FatFS 长文件名的前提下恢复 SD 卡照片保存。
- 消除由主循环持续占用 CPU0 引起的任务看门狗报警。
- 保持 640×480 摄像头分辨率、现有手势识别逻辑和现有单任务状态机结构。
- 不关闭或延长任务看门狗。

## 设计

### SD 存储路径

将存储根目录从 `/sdcard/smartscore` 改为 `/sdcard/score`。`score` 不超过 8 个字符，可直接用于当前 FatFS 8.3 配置，不增加长文件名缓冲区或额外内存开销。

会话目录和照片路径继续由现有代码在该根目录下生成，例如 `/sdcard/score/session_0001/img_000001.jpg`。

### CPU 协作式调度

保留现有 `app_main` 架构，并增加两个明确的调度让出点：

1. JPEG 解码完成后执行一次 `vTaskDelay(1)`，让 CPU0 的空闲任务能在进入 AI 推理前运行。
2. 每轮已处理图像循环结束前再执行一次 `vTaskDelay(1)`，避免连续到期的 AI 周期形成无阻塞循环。

这两个让出点只增加约一个系统 tick 的调度机会，不改变动作判断、照片周期或模型接口。

## 错误处理

- SD 卡挂载或短目录创建失败时，保持现有降级行为：禁用照片保存，但继续运行手势识别。
- 摄像头取帧失败时，保持现有警告和短延迟逻辑。
- 不通过喂狗、关闭看门狗或延长超时时间掩盖任务饥饿。

## 验证

1. 使用 ESP-IDF 5.4.4 完整构建项目并确认生成固件。
2. 检查构建使用 `idf5.4_py3.12_env` 和 ESP-IDF 5.4.4。
3. 静态确认存储根目录为 `/sdcard/score`。
4. 静态确认 JPEG 解码后和主循环末尾均存在调度让出点。
5. 烧录后的成功标准：日志出现 SD 卡挂载成功，且持续运行时不再出现 `IDLE0` 任务看门狗报警。

## 非目标

- 不重构为多任务 AI 管线。
- 不修改摄像头分辨率、JPEG 质量、模型或手势状态机。
- 不处理 ESP-IDF 仓库遗留的 Git 子模块版本警告。
